# 06 — Release for the 2026/27 year: admissions, fees, hostel, postponement

**Time:** about 1 hour, including setup in the app. **When:** outside school
hours, before admissions open for 12 October 2026. **Where:** laptop, then server.

This release covers the admissions desks, the payment schedule (the awamu form),
hostel, required items, postponement and finishing, and the college's offices
(DPARC, DPFPA, ICT officer, the exam officer as an office of its own). It adds
database migrations 0045 to 0060, depending on how far the server already is. 0056 adds
the VETA courses (intakes, course fees, course applications) and the expenses register;
0057 the "paid before admission" mark on course fee instalments; 0058 the Form Four
index number, students' health records, the Dean of Students office, the repeaters'
direct cost, and expense queries and petty cash; 0059 a field for the authority's
supplementary-sitting grade; 0060 the security fixes (password-reset log, sign-in
lockout, receipt file types). It moves Django to **5.2 LTS** (`deploy.sh` installs it
from `requirements.txt`) and needs **no new
Python packages and no new settings**. Guide 03 still does the deploy itself;
this guide covers what comes before and after it.

## B. On the server

**0. Before the deploy: the secret key must be set.** The app now refuses to start
without a real `SECRET_KEY` (anybody who knows the default could forge a session).
Check the server's `.env` has one — this prints `1`, never the key:

```
$ sudo grep -c '^SECRET_KEY=.\{30,\}' /var/www/edutrack/backend/.env
```

If it prints `0`, add a line `SECRET_KEY=` followed by the output of
`python3 -c "import secrets; print(secrets.token_urlsafe(50))"`, before deploying.

**After the deploy: run the Ansible playbook once** (`ops/ansible`, as in guide 01).
It installs the new nginx request limits (sign-in 5 a minute, API 20 a second per
address) and gunicorn's 3 workers × 4 threads. `deploy.sh` alone does not change
nginx or the service file. Then `sudo nginx -t` must say *ok*.

**1. See what this deploy will change.**

```
$ cd /var/www/edutrack/backend
$ sudo -u bphacoh venv/bin/python manage.py showmigrations attendance | tail -12
```

Every migration after the last `[X]` is applied by the deploy.

**2. Find out which accounts are superusers.** Migration 0055 gives every
account that works as the exam officer today its own Exam Officer role, and
then takes Django's `is_staff` flag off everyone except superusers. Nobody loses
their work, but you need to know who the superusers are for step C2 (only your
ICT account should stay one):

```
$ sudo -u bphacoh venv/bin/python manage.py shell -c "from django.contrib.auth.models import User; print([u.username for u in User.objects.filter(is_superuser=True)])"
```

**3. Send a fresh backup off the server first.** This release is big.

```
$ sudo edutrack-backup
```

**4. Deploy** (guide 03):

```
$ sudo edutrack-deploy
```

It stops and prints the commands to go back if any step fails. See guide 03,
"Going back".

**5. Load the year's fees and instalment dates (once).**

First look in the app: Finance ▸ Fee Setup ▸ Fee Structure, year 2026/2027.

- **Empty:** load the published fee structure:
  ```
  $ sudo -u bphacoh venv/bin/python manage.py seed_fee_structure --year 2026/2027 --first-due 2026-10-19
  ```
- **Already filled in by the accountant:** do *not* run it. It would overwrite
  their amounts with the published ones.

Then load the instalment dates from the "Fomu ya tarehe za awamu za malipo":

```
$ sudo -u bphacoh venv/bin/python manage.py seed_payment_schedule --year 2026/2027
```

You should see nine lines ending `matches the form`. If the fee amounts differ
from the form, it saves nothing and says so.

## C. Setup in the app, before admissions open

**1. The offices (Principal).** Sign in as the Principal, open **User
Accounts** and check the exam officer's row now says *Exam Officer*. Then
create the new offices. Only the Principal can give these roles:

| Account | Role to give |
|---|---|
| You (ICT officer) | ICT Officer — this also opens Django admin to you |
| Deputy Principal Academic | DPARC |
| Deputy Principal Finance | DPFPA |
| Dean of Students | Dean of Students — reads students' health records |

Every role change is listed under **Role changes** on the same page.

**2. Django admin is the ICT officer's (you).** The ICT Officer role makes the
account a Django superuser, so `/admin/` opens with every table, and a
**Django Admin** link appears in the menu. Inside EduTrack the account still
sees the ICT officer's screens only (accounts and passwords, not marks or
money). Taking the role away takes `/admin/` away with it.

- If the Principal gave *your* account the ICT Officer role in step 1, you are done.
- If you have been signing in with the old shared superuser (the exam office's
  account), sign in to `/admin/` as yourself, open **Users**, and on that
  account untick **Superuser status** and **Staff status**. The migration has
  already given it the Exam Officer role, so the exam office keeps working —
  from the morning after the deploy it already shows only the exam officer's
  menus; unticking takes away `/admin/`.
  Leave no superuser except yours.

There is no sealed emergency password to keep. If your account is ever locked
out, the way back is on the server, which only you can reach:

```
$ sudo -u bphacoh venv/bin/python manage.py createsuperuser
```

**3. VETA courses (first intake: cosmetology, 19 October).** In this order:

| Who | Where | What |
|---|---|---|
| Principal | User Accounts | Give the training coordinator the **Course Coordinator** role |
| Principal or DPARC | Departments | Add the department if new, then each course: name, code, **structure** (VETA short course, or VETA long course to NVA Level I–III), **duration** in months |
| You (server) | after the department exists | `sudo -u bphacoh venv/bin/python manage.py seed_veta_courses --year 2026/2027 --department <CODE>` — the two cosmetology courses and every fee on the form; it prints `matches the form` three times |
| Accountant | Fee Setup ▸ Course Fees (VETA) | Check the fees; change what must be paid before admission if needed (the seed marks awamu 1) |
| Admission officer | Admissions ▸ Window & ID numbers | The **pattern for VETA courses** (blank = the same as PST) |
| Admission officer | Admissions ▸ VETA courses | Open the intake (start date; the end date follows the duration) |
| Course coordinator | VETA Courses | The course's modules |

Students then go through Admissions ▸ VETA courses: intake → records (a phone and a
next of kin; no documents) → finance (day or hostel, raise the fees) → admission
(the college ID and a portal password). They sign in at the usual login page with
their college ID.

**4. Expenses.** The accountant adds the categories and this year's budget for each
(Finance ▸ Expenses ▸ Categories & Budget). From then on every expense is requested
there, from **office funds** or **petty cash**, and waits for the Principal or DPFPA
(Executive Summary ▸ Spending), who approve, reject or **query** it. The accountant
records the opening petty cash float as a top-up (Finance ▸ Expenses ▸ Petty cash,
drawn from a bank account) before the first petty-cash payment.

**4a. What a repeater pays (accountant, Fee Setup).** Repeat Module is 200,000 per
module and there is a new yearly direct cost of 280,000 for students repeating
failed modules only. On a server where the fee structure is already loaded, set
them by hand rather than re-running the seed, which would put every amount back
to the form's:

| Where | What |
|---|---|
| Charge Types ▸ Repeat Module | *Raised by declaration*: **Repeat module** (if not already) |
| Fee Structure | Repeat Module: **200,000** at each level, one instalment |
| Charge Types ▸ new | **Repeat direct costs**: family *Direct Costs*, applies *On request*, the other-charges account, blocks registration, tick **Bill it once a year to a student repeating failed modules only** |
| Fee Structure | Repeat direct costs: **280,000** at each level, one instalment, with its due date |

On a fresh server `seed_fee_structure` loads both.

**4b. Last year's returning students (examination officer, before admission).**
Readmissions, repeaters and postponement returns from before the system have no
results in it, so admission would bill them wrongly. The examination officer (or the
Principal / DPARC) enters each from the papers — NACTVET's results sheet, the
postponement letter — on **Returning Students**: one at a time, or a whole sheet from
the Excel template (Registration Number, Name, Kind, Programme, Level, Semester,
Modules). Then the admission officer finds them under **Admissions ▸ Expected back**:

| Entered as | Button at admission | Billed |
|---|---|---|
| Readmission | Start readmission | as a new student; sits the semester afresh |
| Repeat (with module codes) | Start their repeat | 200,000 per module + 280,000 once a year; only those modules, as repeat sittings |
| Postponed | Start their return | as continuing |
| Postponed, and was repeating (with module codes) | Start their return — the list shows "repeating …" | as a repeater: 200,000 per module + 280,000; only those modules |

A **new student starting at level 5 or 6** (holding the level below from elsewhere) needs
nothing special: open a *First year* application at that level. They are billed as a new
student, the one-time charges included (the fee form's "new entrants at 5 and 6"), and
sit that level's modules.

Every entry carries the paper it came from. A student whose results the system
already holds is refused (their semester review decides), and a module code not
offered this year is refused with the reason.

**5. The year's setup.** In this order. Each office signs in with its own account.

| Who | Where | What |
|---|---|---|
| Principal / admin | User Accounts | Accounts for the **admission officer** and the **records officer** |
| Accountant | Fee Setup ▸ Charge Types | **TPH Book**, **Calculator**, **Rim Paper**: family *Other*, applies *On request*, the other-charges bank account |
| Accountant | Fee Setup ▸ Fee Structure | A rate for each of those at every level |
| Accountant | Fee Setup ▸ Payment Schedule | Check both schedules. **Confirm which "michango mingine" make up the new students' second instalment of 350,000.** The seed put research/field fees, the semester II national exam and graduation fees there |
| Admission officer | Admissions ▸ Window & ID numbers | The admission window for Semester 1 2026/27, the college ID format, and **Required items**: TPH Book, Calculator, Rim Paper (every semester) and **Insurance** billed under *Medical fees (Health Insurance)* (once a year) |
| Admission officer | Admissions ▸ My desk | If continuing students aren't queued at finance yet: **Send continuing students to finance** |
| Accountant | Each continuing student's application | Students already living in the hostel: press **Hostel**. Last year's hostel students aren't in the system, so this year it has to be done by hand |

## What staff will notice

- **Registering needs the first instalment paid.** This counts the charges ticked
  *blocks registration*, even before 19/10. Items (TPH, calculator, rim paper,
  insurance) never block anything. They are debts only.
- **Every office sees only its own desks.** Only the admission office and the
  Principal see the whole admissions queue.
- **Each other fee has its own invoice:** the supplementary exam, the special
  exam, a repeat module, the TPH book, and anything else raised on request. Each is
  offered only to a student billed for it.
- **Passwords last six months.** Every staff member's clock starts the first time
  they sign in after this deploy, so nobody is locked out on the day.
- **Postponement** is approved only by the Principal. It reverses that period's
  fees, and what the student paid is carried to their return as credit. The
  Principal and DPARC get a notice for every request.
- **The exam office works from the departments' lists.** Registering modules,
  enrolling students, the staff list, forms and service requests, and sick
  records are the HOD's, DPARC's and the Principal's. The exam officer reads this
  semester's modules and class lists.
- **The exam officer no longer manages accounts or advances the semester.**
  Accounts and passwords are the ICT officer's (with the Principal). Confirming
  the semester review and advancing are the Principal's and DPARC's; the exam
  officer prepares the review.
- **Only the ICT officer and the Principal set or reset passwords**, and only they see a
  temporary one (User Accounts ▸ Password desk). Anybody who has forgotten a password —
  staff, the Principal, students — gets one there, shown once, and must choose their own
  at the next sign-in. Every reset is in the desk's log and in the holder's
  notifications. Nobody else — not admission, records, tutors or Heads of Department —
  can set a student's password.
- **Admission no longer hands out a portal password.** After admitting, the ICT officer
  presses *Issue passwords to students who have none*: every newly admitted student gets
  their own, listed once with Download (Excel) and Print slips. Plan it for the admission
  days (12 and 19 October).
- **Signing in pauses after 10 wrong passwords** for the same name (or 100 from one
  address) for 15 minutes. The message says to wait or see the ICT officer.
- **Sessions end after 8 hours**, and when the browser closes.
- **Expense receipts are PDF, JPG or PNG**, and open as a download.
- **Medical certificates** are seen only by records, the Dean of Students and the Principal.
- **Results follow NACTVET exactly** (checked on 188 real students of 2024/25; 187 match):
  - the GPA counts every grade at its own letter, a starred one too (B\*\*\* is 3, D\* is 1),
    and is **cut** to one decimal as NACTVET prints it (2.89 shows as 2.8);
  - GPA below 2.0 is a discontinuation, checked first;
  - more than half of the modules failed (the field module counts) means repeating them,
    no supplementary; half or fewer go to supplementaries;
  - a module failed at its **repeat** sitting, starred or not, is a discontinuation at once;
  - level 6 classes: First from 4.4, Upper Second 3.5, Lower Second 2.7, Pass 2.0.
  The Semester Review, the Results Summary, the student's portal and the Exam Declarations
  screen all read the same decision. No result is changed.
- **Supplementary sheets are uploaded as the supplementary sitting.** On Results ▸
  Authority Grade Import, choose *Supplementary sitting* (a sheet whose exam numbers contain
  RSM is recognised by itself). Only the modules that were waiting for a supplementary are
  taken; the first sitting's grade is kept; a paper still starred there is repeated.
- **A readmitted semester is sat afresh:** after a discontinuation, every module of that
  semester is a first sitting again, under first-sitting rules.
- **The field module is "Pharmacy Practice", 5 credits**, at every level (PST04213,
  PST05211, PST06212). Check the server's modules carry that before results are uploaded.
- **The Form Four index number is required** for a first year at the records desk
  (written like `S0123/0045/2021`); continuing students without one are flagged,
  not held. **Gender** is now required at the VETA records desk too.
- **Health problems** are recorded by records against a verified medical
  certificate, and the Dean of Students is told and reads them. Nobody else sees
  them except the Principal.
- **A repeater pays 280,000 once a year plus 200,000 per module** sat again, and no
  programme fees.
- **Expenses can be queried.** The Principal or DPFPA may ask the accountant a
  question instead of deciding; the accountant answers (and may correct the amount)
  and it waits again. Each expense says whether it comes from office funds or
  petty cash; petty cash is paid in cash, never beyond the float.
- **Marks go by module.** Whoever teaches a module enters its CA, whatever other
  office they hold (a teaching HOD now can, which was refused before). The
  Principal no longer approves results; the exam officer does.
- **The marks sheet's Save button now keeps to the CA window**, as saving one
  result always did. Before tutors enter CA, the exam officer must open the CA
  window (Results ▸ *Mark entry windows*), or Save reports that marks are
  closed.
